# Product Vision (초안)

> ⚠️ **본 문서는 초안입니다.** 실제 서비스 적용 전 제품·법무 검토가 필요합니다.

## 1. 서비스의 존재 이유
중소 사업자, 1인 운영자, 동호회·교육기관 등은 자신의 웹사이트(회사 소개, 블로그, 예약, 회원 전용 등)를 빠르게 만들고 운영해야 한다. 그러나 직접 개발은 비용·시간·운영 부담이 크고, 기존 빌더형 SaaS는 종속성이 강해 데이터를 자유롭게 가져갈 수 없다.

이 SaaS는 **"빠르게 만들 수 있고, 언제든 자기 서버로 가져갈 수 있는"** 두 가지 가치를 함께 제공한다.

## 2. 고객이 얻는 핵심 가치
- 사이트 유형(회사 소개 / 블로그 / 예약 / 회원 전용 / 교육 등) 선택 → 위저드 → 즉시 운영 가능한 사이트 발급
- 데스크탑 중심 관리자에서 컨텐츠·메뉴·예약을 직접 운영
- 운영 중 언제든 **export**로 코드·DB·설정 일체를 내려받아 자체 서버로 이전 가능
- 성장 시 dedicated DB / dedicated Docker stack으로 점진적 승격 가능 (lock-in 최소화)

## 3. 왜 SaaS로 먼저 운영하는가
- 고객의 즉시 사용성: 인프라 구축·도메인·SSL·DB 운영 부담 제거
- 운영자(우리)의 학습 루프: 다수 테넌트의 사용 패턴을 빠르게 관찰·반영
- 비용 효율: 초기엔 shared infra로 단가 절감, 성장 고객만 dedicated 전환

## 4. 왜 export를 지원하는가
- **반-lock-in 약속**: 고객은 자기 데이터의 주인. SaaS는 운영 편의 제공자
- 신뢰 기반 영업: "언제든 떠날 수 있어야 들어올 수 있다"
- 법적·정책적 안전판: 서비스 종료, 정책 변경 시 고객 보호장치
- 장기 전환 경로: 고객 성장 → dedicated stack 또는 자체 서버 운영으로 자연 승격

## 5. 단기 MVP 방향
- 멀티테넌트 shared MySQL + `site_id` 분리
- 사이트 유형: 회사 소개, 블로그, 예약(알림 없음)
- 관리자 UX: 데스크탑 전용
- 인증/RBAC: owner / admin / editor / viewer
- 기본 export: 사이트 컨텐츠·설정 zip + DB dump (수동 트리거)
- 결제·청구·알림(카카오/이메일) MVP 제외

## 6. 장기 확장 방향
- dedicated DB → dedicated Docker stack 승격(같은 코드베이스, 격리만 변경)
- 고객 자체 도메인·SSL 자동화
- 카카오 알림톡·이메일·SMS 어댑터(이벤트 기반 연결)
- 템플릿 마켓플레이스, 유료 템플릿
- 결제·청구(Stripe/토스)·세금계산서 연동
- API 공개(웹훅·외부 통합)
- export 자동화 + 셀프 호스팅 가이드 + 공식 마이그레이션 지원

## 7. Non-goals (지금은 하지 않는다)
- 모바일 최적화 관리자 (데스크탑 전용 유지)
- 디자인 자유도 극단 추구(코드 에디터형 빌더, 픽셀 단위 편집)
- 자체 호스팅 전용 라이선스 판매 모델
- 외부 기업 시스템 통합 일반화(특정 ERP/CRM에 깊이 묶이지 않음)
- 즉시 삭제(hard delete) 기본화 — 정책상 유예·export 우선

## 8. 정책-아키텍처 정합성
- shared → dedicated 승격 가능성을 전제로 **모든 DB 접근은 connection resolver 경유**
- export 가능성을 전제로 **사이트 데이터는 site_id로 완전 격리** (교차 참조 금지)
- 해지 시 즉시 삭제가 아닌 **유예 → export → 삭제** 순서가 코드/스키마 수준에서 표현됨 (`status: active | suspended | grace | terminated`)
